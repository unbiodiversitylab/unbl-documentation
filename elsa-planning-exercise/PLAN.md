# Plan: an interactive planning exercise in the ELSA documentation

Branch: `elsa-planning-exercise` · Status: **phase 1 built (both tabs, five languages), unpublished** · Nov 2026

This plan turns the draft "Interactive Conservation Planning Exercise" design
(adapted from Trevor Wiens' *Conservation Planning Exercise*, the "Marxan Demo")
into a page of the ELSA user guide, in all five languages. Nothing is published
until the permissions in section 7 are recorded.

---

## 1. Summary

We build a hands-on page, **"Try It First: A Hands-on Planning Exercise"**, in the
ELSA section, right after chapter 2. It has **two tabs**, so readers can explore
both ways of asking the planning question:

- **Lowest cost**: the original Marxan-style puzzle (meet every target at the
  lowest score, with a boundary penalty).
- **Most value in the area available (ELSA-style)**: the problem the ELSA tool
  solves (area-based targets per action, action zones, lock-in, weights, BPF).

The exercise is part of the MkDocs site. It is not a separate app. It uses plain
JavaScript with no libraries, no Node build and no requests to other sites. Its
explanatory text lives in normal `.md` pages, so the existing translation
workflow and drift tracking apply. A build hook also produces a single offline
HTML file per language for workshops.

The draft is solid on purpose, credit and permissions. Keep its permission

need to change before we build:

## 3. What readers will experience

Decided 10 Nov 2026: one page with two tabs (Material content tabs), in all five
languages. The four "rounds" of the earlier draft are folded into the two tabs.

**Tab 1 – Lowest cost.** Click planning units to meet targets for features A, B
and C. Panel: target, selected amount, shortfall, and
cost + boundary penalty + shortfall penalty = score (lower is better). A view
selector shades the grid by cost or by one feature. A BPF selector (0, 1, 3, 10)
shows how compactness changes the answer.

**Tab 2 – ELSA-style.** Choose an action (Protect, Restore, Manage), then click
planning units. Each action has an area-based target (a cap), is only allowed on
some land types (action zones), and the existing protected area is locked in for
Protect (can be turned off). Views: land type, heatmap (weighted value), each
feature. Settings: area-based targets and weights (0–10). Score: weighted value
minus boundary penalty (higher is better).

**In both tabs:** *Let the computer search* animates simulated annealing on the
grid (each run differs), *Show the best answer* shows prioritizr's answer, and a
comparison table puts your map, the search and the best answer side by side.
Your own map is kept while you look at the others, and *Copy to my map* lets
you start from the computer's answer. "What this means in ELSA" boxes link to
chapters 5 and 7 and Annex 1.

**After the tabs:** why a computer is needed (2^100 combinations; heuristic
versus exact; ELSA's 5% gap), and next steps.

Decided: nothing is saved or sent. No scores are recorded.

## 4. How it fits the docs

### 4.1 Files

```
docs/elsa/
  planning_exercise.md (+ .es .fr .pt .ru)  the page: all prose, headings, credit, alt text
  exercise/
    exercise.js         the app (grid, scoring, rounds, SA solver), about 30 KB, no libraries
    exercise.css        styles, using Material's CSS variables (light/dark)
    loader.js           1 KB, in extra_javascript; loads the two files above only on this page
    grid.json           placeholder grid, targets, zones, lock-ins, precomputed solutions
    strings.json        short UI labels (buttons, panel labels), English
    strings.es.json ... strings.ru.json     the same keys, translated
  images/planning-exercise-01.png ...       static screenshots: the fallback if JS is off, and for print

elsa-planning-exercise/            development files, not part of the site
  PLAN.md                          this file
  PERMISSIONS.md                   approval record (from draft §4.1)
  make_grid.py                     generates grid.json from a fixed seed (Python, standard library only)
  solve.R                          prioritizr solutions (min-set, BPF sweep, ELSA-style zones) written into grid.json
  README.md                        how to regenerate data, how to test

hooks/planning_exercise.py         after the build: writes site/<lang>/elsa/exercise/offline.html (inlined, one file)
```

- **File name** `planning_exercise.md` has no number prefix (like
  `unbl-workspaces/data_security.md`), so no existing chapter is renamed and no
  WordPress deep link breaks.
- **Nav:** after "Tool Purpose and Key Features", titled *"Try It First: A Hands-on
  Planning Exercise"*, with `nav_translations` in all four locale blocks.
- **Linked from:** the ELSA index, chapter 1 (science resources), chapter 5 (BPF and
  weights sections: "Try it in the exercise"), Annex 1 entries for BPF, planning
  units and weights, and What's new.

### 4.2 Why the loader

The build experiment on this branch found that the i18n plugin copies only files
a page references into each language folder. `/fr/elsa/exercise/exercise.js`
doesn't exist unless we make it. So `loader.js` goes in `extra_javascript`
(served correctly on every language). It does nothing unless the page has
`<div id="planning-exercise">`. When it does, it loads `exercise.js`, `exercise.css`
and `grid.json` from its own folder, and `strings.json` from the page's language
folder (`<html lang>`). The translated `strings.fr.json` is served as
`/fr/elsa/exercise/strings.json` (tested). Other pages pay about 1 KB, cached.

### 4.3 What lives where (for translators)

- **Everything a reader reads as text** (round intros, "What this means in ELSA"
  boxes, credit, alt text) is in the `.md` page and translated normally with
  `/translate`, `source_rev` and drift tracking.
- **Short interface labels** (about 40: "Reset", "Shortfall", "Run", "Score (lower is
  better)") are in `strings.<lang>.json`. Translators change only the right-hand side.
  `check_docs.py` catches a missing key, broken JSON or a lost `{placeholder}`.

### 4.4 Permission gate (this matters)

Until approvals are recorded, `mkdocs.yml` gets:

```yaml
draft_docs: |
  elsa/planning_exercise*.md
```

Tested on this branch: `mkdocs serve` shows the page for development and review,
while `mkdocs build --strict` (CI and production) leaves it out and still passes.
So the work can be merged to `main` in steps without being published. We publish
by deleting those two lines, in a PR that also updates `PERMISSIONS.md`.

### 4.5 Quality rules

- Works at 320 px wide (cells about 28 px), in light and dark mode, and in the WordPress iframe.
- Keyboard: arrow keys move through the grid, Space/Enter selects, visible focus.
  Each cell has a label such as "Row 3, column 7: cost 120, A 14, B 0, C 6, selected".
  Feature amounts are shown as numbers or patterns too, never by colour alone.
- Page weight: under 60 KB of JS + CSS + JSON in total, no fonts, no CDN.
- Numbers formatted per language (`Intl.NumberFormat(lang)`).
- Without JavaScript: the screenshots and text still explain the exercise.

## 5. Checks and CI

Additions to `scripts/check_docs.py` (errors fail CI as usual):

1. **Strings parity:** `strings.<lang>.json` exists for every language, parses, has
   exactly the English keys and the same `{placeholders}`.
2. **Data consistency:** `grid.json` matches its schema (100 units, every feature,
   zone and lock-in present). Every stored solution's cost, boundary and score are
   recomputed by a Python copy of the scoring rule and must match. This catches a
   mismatch between `solve.R` and the JS rules.
3. **Permission guard:** if the page is *not* in `draft_docs`, `PERMISSIONS.md` must
   show all approvals as received. That stops anyone publishing by mistake.
4. **Original-data guard:** `grid.original.json` may not exist while approvals are pending.
5. Drift for `strings.*.json`: a `_source_rev` key, reported by `--drift` like pages.

Testing the JS: a small `exercise.test.html` page (opened locally, no build
tools) runs the scoring against the same stored solutions. There's also a manual
QA checklist in `elsa-planning-exercise/README.md`: five languages, mobile, dark
mode, keyboard only, screen reader spot check, and inside the WordPress iframe.

## 6. Translation and terminology

Add to `i18n/glossary.yml`, taking the wording from the published Annex 1 pages:

| en | es | fr | pt | ru |
|---|---|---|---|---|
| planning unit | unidad de planificación | unité de planification | unidade de planeamento | планировочная единица |
| planning feature | característica de planificación | caractéristique de planification | característica de planeamento | планировочный элемент |
| boundary penalty factor (BPF) | factor de penalización de los límites | facteur de pénalité de limites | fator de penalização de fronteira | коэффициент граничного штрафа |
| weight | ponderación | pondération | peso | вес |
| lock-in | bloqueo | verrouillage | bloqueio | блокировка |
| action zone | zona de acción | zone d'action | zona de ação | зона ограниченных действий |

New terms that need translator decisions: *target (feature, Marxan sense)*,
*shortfall*, *cost*, *score*, *clumped / unclumped*, *heuristic*, *exact solver*. Note
that ELSA's *area-based target* (*objectif basé sur les zones*) is a cap on area,
while Marxan's *target* is a minimum amount. They must not get the same word in
any language. Draft suggestion: EN "feature target", FR "cible", ES "meta de
representación", to be confirmed. PacMARA's 2020 Spanish materials (*objetos de
conservación*, *metas*) are worth consulting, but the published ELSA pages take
priority.

Process: English frozen → `/translate` (machine drafts, `translation_status:
machine`) → `translation-reviewer` agent → native review via the existing review
issues (#49 ES, #65 FR, #50/#51 PT/RU), ideally by someone who knows SCP.
